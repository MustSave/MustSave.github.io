연수 과정에서 팀매칭 페이지를 사용하다가 다른 연수생이 입력한 `<marquee>` 태그가 화면에 적용되는 모습을 봤습니다. 스크립트는 아니었지만 HTML 태그가 동작하는 것을 보고, JavaScript도 실행될 수 있지 않을까 하는 호기심에 여러 입력을 시험해 봤습니다. 처음에는 일반적인 alert 실행 입력이 필터링되어 실행되지 않았지만, 입력 형태를 바꿔 가며 시도하다가 JavaScript가 실행되는 경우를 찾았습니다. 이때는 필터가 문자열 일부를 지우면서 오히려 실행 가능한 코드가 만들어졌습니다.

## 지우기 전과 지운 후의 문자열

당시 보고서에는 `alert`라는 문자열을 한 차례 제거하는 동작이 원인으로 보인다고 적었습니다. 이 동작을 문자열 변환으로 나타내면 다음과 같습니다.

```text
입력               alert 제거 후
<scralertipt>      <script>
alealertrt()        alert()
</scralertipt>     </script>
```

`<scralertipt>`는 `scr`과 `ipt` 사이에 `alert`가 들어간 형태입니다. 여기서 `alert`를 제거하면 양쪽 문자열이 붙어 `<script>`가 됩니다. 함수명도 마찬가지입니다. `alealertrt()`에서 중간의 `alert`를 제거하면 `ale`와 `rt()`가 이어지면서 `alert()`가 만들어집니다.

입력 당시에는 완성된 태그와 함수명이 아니었던 문자열이 필터를 거치면서 실행 가능한 형태로 바뀐 셈입니다. 저는 이 형태의 입력을 본인 팀에 넣었고, 저장된 내용을 표시하는 페이지에서 JavaScript가 실행되는 것을 확인했습니다.

즉, 필터가 `alert`를 지웠는데도 최종 결과에는 `alert()`가 남았습니다. 지우기 전에는 `alealertrt()`였지만, 중간 문자열을 제거하면서 남은 조각이 이어져 함수명이 다시 만들어졌기 때문입니다. `<script>` 태그도 같은 방식으로 만들어져 브라우저에서 코드가 실행됐습니다.

## 입력한 팀과 실행되는 화면의 범위

테스트 입력은 본인 팀에 넣었지만, 해당 팀 정보는 다른 연수생도 확인할 수 있는 목록에 표시됐습니다. 따라서 저장된 입력의 영향은 제 화면에만 한정되지 않았습니다. 다른 연수생이 보는 목록에서도 실행 가능한 상태였기 때문에, 확인 후 입력을 삭제하고 메일로 재현 방법과 위험을 제보했습니다.

저장형 XSS에서 중요한 것은 입력을 누가 소유하는지뿐 아니라 그 입력을 누가 보게 되는지입니다. 본인 팀의 이름을 수정할 수 있는 권한과, 그 이름을 보는 다른 사람의 브라우저에서 코드를 실행하는 것은 서로 다른 범위의 행동입니다. 제 팀에 입력했다는 사실만으로 테스트가 제게만 영향을 준다고 볼 수는 없었습니다.

당시에는 호기심으로 직접 확인해 봤지만, 앞으로 비슷한 상황을 만나면 관찰한 현상과 의심되는 위험을 먼저 메일로 제보하거나 담당자에게 테스트 허가를 구해야겠다고 생각합니다. 추가 확인이 필요하다면 허용된 테스트 범위와 환경을 정한 뒤 진행하는 편이 적절하겠습니다.

## HttpOnly가 막는 것

당시 확인한 세션 관련 쿠키에는 HttpOnly가 설정되어 있었습니다. 보고서에서도 이 점을 언급했지만, 쿠키를 JavaScript로 읽지 못한다는 사실과 XSS의 영향이 사라진다는 것은 다릅니다.

HttpOnly는 스크립트의 쿠키 읽기를 막습니다. 그러나 브라우저가 쿠키를 포함해 서버에 요청하는 동작까지 막지는 않습니다. 페이지 안에서 실행된 코드는 접근 가능한 화면 데이터를 읽거나 인증된 요청을 시도할 수 있으므로, 쿠키를 직접 가져갈 수 없더라도 위험은 남습니다. [OWASP의 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)도 이 차이를 설명합니다.

## 반복해서 지우면 해결될까

당시에는 HTML 태그가 동작하면서도 스크립트 입력은 필터링되는 것을 보고, 연수생들이 여러 HTML 태그로 팀 정보를 꾸미며 놀 수 있도록 의도적으로 허용한 것이라고 생각했습니다. 그래서 태그 사용은 유지하면서 실행되는 코드를 막을 수 있는 방법으로, 더 이상 문자열이 바뀌지 않을 때까지 필터링하는 방안을 제안했고 escape 처리도 함께 언급했습니다.

반복해서 제거하면 이 예시에서 새로 만들어진 `alert`를 다시 지울 수는 있습니다. 하지만 특정 문자열을 계속 지우는 방법만으로 브라우저가 해석할 수 있는 여러 실행 구문을 다룰 수 있는 것은 아닙니다.

팀명이나 프로젝트명을 글자로 표시하려는 경우라면, 입력을 HTML로 해석하지 않는 출력 방식이 적합합니다. 예를 들어 일반적인 `div` 요소에 문자열을 넣을 때는 다음처럼 표현할 수 있습니다.

```javascript
const teamNameElement = document.createElement('div');
teamNameElement.textContent = '<marquee>팀 이름</marquee>';
```

이 예시에서는 `<marquee>팀 이름</marquee>`가 태그로 동작하지 않고 그대로 텍스트로 표시됩니다. 서버 템플릿에서는 출력 위치에 맞는 인코딩을 적용하고, HTML 입력 자체가 필요한 기능이라면 적절한 HTML sanitizer를 사용해야 합니다. [OWASP의 XSS 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)은 출력 맥락에 맞는 인코딩, 안전한 출력 API, HTML sanitization을 구분합니다.
